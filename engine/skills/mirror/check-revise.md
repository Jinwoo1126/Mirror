# Check, revise and return understanding to help

Load before a material candidate is persisted, on relevant feedback, or when `prepare` returns unreviewed experience. The same host performs this semantic check using **only observed dialogue, accessible source events, provisional alternatives and actual feedback**. Never consult a hidden synthetic persona, evaluator answer or private psychological target. Store validation checks structure/provenance references, not truth. This procedure is not an independent quality review or an extra model call.

## Check the candidate against the observed record

- Verify each claim's source attribution, role and time boundary. Distinguish direct observation, explicit self-report and inferred explanation. Quotations, hypotheticals and third-party experiences are not automatically user facts. Include the original assistant premise when interpreting feedback; a response to an assistant-supplied interpretation is not independent evidence of a pre-existing motive. Preserve earlier explicit reasons/corrections and mark possible influence instead of discarding the whole exchange.
- Compare support with contrary experiences, exceptions and a plausible ordinary task/instrumental explanation. For a deeper relationship, identify the supported connection and what help it could change; do not accept a paraphrased preference or elegant wording as causal evidence. Check whether a proposed cross-domain transfer is actually supported or still untested. Retrieve again through [select](select.md) only when accessible evidence could settle a material gap.
- Later feedback may support, narrow, contradict or leave the candidate unresolved. Evidence used to form a claim is not later validation. Silence is not agreement; a forecast is not an observed outcome; acceptance of a useful answer alone does not establish its psychological explanation. Do not call disagreement a defense mechanism or discard an explicit correction to protect a hypothesis.
- Compare the complete proposed card against its prior body and the triggering evidence. Check statement, reason **and** conditions together: replace stale scope/time/offer wording, do not merely append a correction that leaves it active. An explicit later commitment can coexist with a historically unaccepted offer only when the episodes are clear. Keep reported events distinct from inferred causal links and pending plans distinct from observed outcomes. Verify that material adopted details claimed as retained are actually present with their source attribution.
- For a synthesized explanation, name the relation added beyond the strongest accurate conditional-rule summary, its supporting visible contrast and a live alternative. If the sources support only the rules, retain those and leave explanatory depth unresolved; neither extra length nor shared boundary language earns a deeper claim.
- Decide `keep`, `narrow`, `revise`, `withdraw` or `unresolved`. Keep unchanged cards without rewriting them. Narrow conditions when evidence is local; revise the responsible explanation rather than the whole person. Withdraw a rejected/replaced claim; unresolved claims must remain explicitly provisional or unpersisted. Missing independent later validation or an unresolved plausible rival alone does not bar retaining a source-supported, useful bounded hypothesis; check provisional eligibility separately from any claim of validation or depth success. Do not invent depth to fill a gap. Respect current requests and stop/delete controls immediately.

## Preserve a small decision trace

For each material candidate/change, retain a concise source-bound record in the existing experiment artifact: affected card ID; **prior understanding snapshot and read revision before the patch** (or explicit absence for a new card); proposed candidate; transition type in the existing trace (`new formation` if no prior active understanding, `retention` if unchanged, or `revision` if its content materially changes; note withdrawal/unresolved separately); triggering source IDs; support and contrary evidence or its absence; scope/conditions; decision (`keep/narrow/revise/withdraw/unresolved`) and short basis, including a material unresolved alternative. Retain the attempted patch and its success/error separately from the **actual resulting understanding and revision**, filled from the post-attempt reread. A failed/stale attempt is not an applied revision; preserve its failure, reread current state, and reconsider before a new attempt. Upsert overwrites a card body, so existing card fields alone cannot preserve before/after history. A `keep` decision that creates an absent card is new formation, not retention or verified revision. Rereading an unchanged checkpoint is retention/no-op, not another insight or independent validation. Report actual transitions separately in existing experiment summaries; add no store field.

Existing `reason`/`conditions`, `evidence`/`counter_evidence` fields may carry the final understanding, but the experiment's normal run artifact retains the prior/candidate/decision/result trace, including withdrawn and unpersisted candidates. For an unpersisted candidate record that no patch was attempted and the prior state remains unchanged. These are decision summaries, not transcripts of internal reasoning. Do not add card keys, a schema, service, mandatory per-turn log or a new gate. No-change turns need no fabricated candidate. Apply the same privacy and user stop/delete controls to artifacts; never use retained history to reconstruct suppressed content.
## Persist and deliver

1. Build only supported changes in the existing card fields: `id`, `statement`, `scope`, `kind` (`observation`, `self_report`, `hypothesis`), optional `reason`/`conditions`, `evidence`, `counter_evidence`. Source IDs must refer to appended events, including at least one user source for each card. Preserve exact boundary numbers/names/phrases. An empty patch is unnecessary when nothing changed and no reviewed cursor needs advancing.
2. Use the latest read's `revision` as `patch.expected_revision`. Appending events changes revision, so read again if needed. Example shape (replace placeholders with actual values): `{"op":"patch","expected_revision":4,"upsert":[{"id":"criterion","statement":"Source-supported criterion","scope":"product","kind":"hypothesis","conditions":"Observed conditions; transfer untested","evidence":["user-event"],"counter_evidence":[]}],"reviewed":{"episode":"episode-id","through_seq":3}}`. Include `reviewed` only through the sequence actually processed; use `prepare.through_seq` when all its returned events were processed. A rejected stale patch requires rereading and reconsidering current evidence, never overwriting newer feedback. Failed changes must not advance review position.
3. For an ordinarily rejected/replaced claim, use `patch.withdraw: [ID]`; omitting it from `upsert` leaves it active. Withdrawal removes it from context and candidate retrieval, retaining events and other cards sharing them. Unknown/already inactive IDs are no-ops; `withdrawn` lists actual changes. Never withdraw and upsert the same ID in one patch. A later explicit upsert may reactivate only with valid unsuppressed evidence. For an explicit stop-use request use `patch.suspend`; for deletion use `delete` with card `ids`. Those suppress shared source evidence; ordinary withdrawal is not a substitute. Never reconstruct controlled entries or use them indirectly. Inspect/correct on request without a questionnaire.
4. After a successful material patch, request relevant `context` again, complete the trace with the actual resulting active cards and returned revision (explicitly note affected cards now absent/inactive), and use the returned conditions and uncertainty for the present/next answer. After a failed attempt, reread current state to record what actually remains; never label the proposed candidate as the result. Select relevant other-scope candidates if needed. This closes select → form → check/revise → patch → context → help. The host makes the answer or authorized action and need not announce a psychological interpretation. Any narrative account of explanatory updates or retained understanding must match the actual persisted, source-supported hypothesis and its kind/conditions; do not let richer final prose imply an update that the store never received. If current-task details come only from dialogue history, attribute them to that history rather than claiming they were retained. A material supported update intended for later use must be persisted and reread before it is reported as such; otherwise leave it provisional/unpersisted in the trace. Do not compensate for missing stored evidence with confident narrative. Apply all established relevant criteria while giving the current request precedence.
5. Repeated closure with no new evidence is a no-op. Deeper synthesis can share existing host reasoning; a separately budgeted call is permitted only under the agreed budget, never merely because a task ended. Record actual calls, elapsed time and tokens when available; unknown cost remains unknown, not zero.
